# Edge B.R.O. — Инструкция по использованию

🇬🇧 [English](README.md) · [Usage Guide](README_USAGE.md) · 🇷🇺 [Русский](README_ru.md) · [Инструкция](README_USAGE_ru.md)

Пошаговое руководство: от голого сервера до управления парком устройств, создания бэкапов, восстановления дисков и генерации Live-CD киосков.

---

## 1. Подготовка сервера

Подойдёт любая x86_64 Linux-машина с Docker. Intel NUC, мини-ПК или полноценный сервер — что есть под рукой.

1. Установите базовую ОС (Ubuntu 22.04/24.04/26.04 или Debian 12/13).
2. Установите Docker:
   ```bash
    # Вариант А: Установка официального Docker CE (Рекомендуется)
    curl -fsSL https://get.docker.com -o get-docker.sh
    sudo sh get-docker.sh

    # Вариант Б: Либо используйте стандартные пакеты дистрибутива
    # sudo apt update && sudo apt install -y docker.io docker-compose-v2

    # Запуск службы и настройка прав пользователя
    sudo systemctl enable --now docker
    sudo usermod -aG docker $USER
   ```
   После добавления в группу `docker` перелогиньтесь.

## 2. Развёртывание оркестратора

### 2.1 Клонирование и настройка

```bash
git clone https://github.com/masseselsev/edge-bro.git /opt/stacks/edge-bro
cd /opt/stacks/edge-bro
cp .env.example .env
```

Отредактируйте `.env` — каждая строка важна:

```env
# ── База данных ──
POSTGRES_USER=postgres
POSTGRES_PASSWORD=<надёжный_пароль_БД>
POSTGRES_DB=borg_orchestrator
DATABASE_URL=postgresql://postgres:<надёжный_пароль_БД>@db:5432/borg_orchestrator

# ── Redis ──
REDIS_URL=redis://redis:6379/0

# ── Borg ──
BORG_PASSPHRASE=<надёжная_парольная_фраза_borg>

# ── Сеть ──
ORCHESTRATOR_IP=192.168.1.10      # IP этого сервера, доступный для edge-узлов
                                   # Можно изменить позже в Настройки → UI

# ── Суперадмин (только при первом запуске) ──
SUPERADMIN_USERNAME=admin          # Логин для веб-панели
ADMIN_PASSWORD=<надёжный_пароль>   # НЕ будет перезаписан, если изменён через UI
JWT_SECRET_KEY=<случайный_секрет>  # Используется для подписи сессионных токенов

# ── Стабильность SSH (опционально) ──
# SSH_KEEPALIVE_INTERVAL=30        # Секунды между keepalive-пакетами
# SSH_KEEPALIVE_COUNT=3            # Пропущенных ответов до разрыва

# ── Шардирование репозиториев (опционально, показаны значения по умолчанию) ──
BORG_SHARD_COUNT=1                 # Независимых Borg-репозиториев. Borg держит
                                   # блокировку репозитория всё время работы
                                   # `borg create`, поэтому один репозиторий —
                                   # это один пишущий узел в каждый момент.
                                   # Значение можно поднять позже, если нужно
                                   # больше параллельных писателей; понизить —
                                   # нельзя.
# BORG_LOCK_WAIT_SECONDS=600       # Сколько prune и delete ждут блокировку
                                   # репозитория, вместо того чтобы упасть
# BORG_CREATE_LOCK_WAIT_SECONDS=60 # То же для бэкапа, намеренно коротко: тот,
                                   # кому блокировка не досталась сейчас, будет
                                   # повторён (см. ниже), а не займёт воркер
# BORG_WRITER_TTL=14400            # Сколько идущий бэкап числится писателем
                                   # репозитория без подтверждения активности

# ── Повторы бэкапа (необязательно, значения по умолчанию) ──
# BACKUP_REPO_BUSY_COUNTDOWN_SECONDS=600   # Через сколько снова спросить
#                                          # занятый репозиторий
# BACKUP_REPO_BUSY_MAX_RETRIES=144         # ~24 часа попыток, затем отказ
# BACKUP_RECONNECT_COUNTDOWN_SECONDS=60    # Через сколько повторить передачу,
#                                          # у которой оборвалась связь
# BACKUP_RECONNECT_MAX_RETRIES=3           # Сколько попыток до сообщения об ошибке

# ── Пути к хранилищам ──
BORG_HOST_DATA_PATH=borg-data     # Docker volume по умолчанию
                                   # Для внешнего хранилища укажите абсолютный путь:
                                   # BORG_HOST_DATA_PATH=/mnt/hdd/borg_data

ISO_CACHE_HOST_PATH=iso-cache     # Кэш базового и клиентских ISO, Docker volume по умолчанию
                                   # Для внешнего хранилища укажите абсолютный путь:
                                   # ISO_CACHE_HOST_PATH=/mnt/hdd/iso_cache

# ── Docker-сеть (необязательно, показано значение по умолчанию) ──
# DOCKER_SUBNET=172.29.13.0/24     # Подсеть собственной сети стека. Меняйте
                                   # только если она пересекается с тем, что
                                   # хост уже маршрутизирует — см. 10.4.
```

> **Про `SUPERADMIN_USERNAME` / `ADMIN_PASSWORD`**: эти значения создают первую учётную запись суперадмина при первом старте. После создания аккаунт живёт в базе данных. Если вы поменяли пароль через веб-интерфейс, повторное изменение `.env` его не перезапишет. Для принудительного сброса: очистите таблицу `users` в PostgreSQL и перезапустите.
>
> 🔑 **Генерация безопасного `JWT_SECRET_KEY`**: Выполните следующую команду для генерации надежного случайного ключа подписи сессий:
> ```bash
> python3 -c "import secrets; print(secrets.token_hex(32))"
> ```
>
> 🌐 **Если ноды не могут достучаться до оркестратора напрямую** (он за NAT без проброса портов): включите **«Оркестратор находится за NAT»** в Settings → Orchestrator Network Addresses. Бэкапы тогда туннелируются через уже открытое SSH-соединение оркестратора к каждой ноде, вместо прямого подключения к IP оркестратора. Это добавляет накладные расходы на шифрование при каждом бэкапе (данные шифруются дважды), поэтому включайте только при реальной необходимости. Это решает проблему только для автоматических/ручных бэкапов Fleet — пейрингу и восстановлению через Live-USB киоск всё ещё нужен свой сетевой путь (например, WireGuard-клиент киоска), если оркестратор недоступен напрямую.

### 2.2 Настройка хранилища бэкапов

По умолчанию бэкапы попадают в Docker named volume (`borg-data`) в `/var/lib/docker/volumes/`. Для серьёзного использования вынесите хранилище на отдельный диск:

```bash
# Создайте директорию на большом диске
mkdir -p /mnt/hdd/borg_data
chown -R 1000:1000 /mnt/hdd/borg_data
```

Затем в `.env`:
```env
BORG_HOST_DATA_PATH=/mnt/hdd/borg_data
```

> ⚠️ Если корневой раздел заполнится, задачи бэкапа будут падать с `Insufficient free space`, а другие сервисы хоста могут сломаться. Для продакшена всегда используйте отдельный том.

Настроенный путь отображается в веб-интерфейсе в разделе **Настройки**.

### 2.3 Настройка хранилища ISO-кэша

Отдельно от бэкапов оркестратор держит ISO-кэш по пути `/opt/data/iso_cache` внутри контейнеров. Там лежит скачанный базовый образ Debian — актуальная сборка Debian stable live, совпадающая по выпуску с пакетами, которые оркестратор кладёт в киоск, — и все собранные образы USB-Kiosk клиента, поэтому закладывайте **от ~20 ГБ**. По умолчанию кэш находится в Docker volume `iso-cache` в `/var/lib/docker/volumes/`.

Чтобы перенести его на отдельный диск:

```bash
mkdir -p /mnt/hdd/iso_cache
chown -R 1000:1000 /mnt/hdd/iso_cache
```

Затем в `.env`:
```env
ISO_CACHE_HOST_PATH=/mnt/hdd/iso_cache
```

**Один диск под оба хранилища.** Если у вас один большой том — например, NFS-раздел, подключённый к маленькой виртуальной машине, — держите их соседними каталогами, а не вкладывайте кэш внутрь пути с бэкапами, где лежат borg-репозитории:

```env
BORG_HOST_DATA_PATH=/mnt/nfs/edge-bro
ISO_CACHE_HOST_PATH=/mnt/nfs/iso_cache
```

Это два независимых bind-монтирования, и общий диск им вовсе не обязателен — ISO-кэш можно вынести на отдельный диск, если так удобнее. Пути внутри контейнера (`/data/borg` и `/opt/data/iso_cache`) фиксированы и менять их не нужно.

Применение изменения — пересборка не нужна, контейнеры просто пересоздаются с новым монтированием:

```bash
docker compose up -d
```

> ⚠️ Смена пути **не переносит** существующие данные. Всё, что уже закэшировано (базовый ISO, собранные клиентские образы), останется в старом месте и будет скачано/собрано заново. Чтобы сохранить данные, скопируйте содержимое перед перезапуском:
> ```bash
> docker run --rm -v edge-bro_iso-cache:/from -v /mnt/hdd/iso_cache:/to alpine cp -a /from/. /to/
> ```

Если кэш находится на корневом разделе системы, панель показывает предупреждение здоровья `ISO_CACHE_ON_ROOT`.

### 2.4 Запуск

#### Вариант А: Запуск готового релиза (Рекомендуется для продакшена)

Локальная сборка не требуется. Скачайте официальные релизные образы напрямую из GitHub Container Registry (`ghcr.io`). Начиная с версии **v1.8.1**, для запуска требуются **строго только два файла** (`docker-compose.yml` и `.env`) — вспомогательный payload для Live-CD киосков упакован прямо в контейнерный образ:

```bash
# 1. Скачивание только docker-compose.yml и .env
curl -fsSL https://raw.githubusercontent.com/masseselsev/edge-bro/v1.8.2/docker-compose.yml -o docker-compose.yml
curl -fsSL https://raw.githubusercontent.com/masseselsev/edge-bro/v1.8.2/.env.example -o .env

# 2. Настройка паролей и параметров
nano .env

# 3. Скачивание образов и запуск
docker compose pull && docker compose up -d
```

*(Флаг `-f docker-compose.yml` нужен только если вы клонировали репозиторий, чтобы проигнорировать файл `docker-compose.override.yml`, предназначенный для локальной разработки).*

#### Вариант Б: Локальная сборка из исходников (Только разработка)

Если вы редактируете исходный код локально:

```bash
docker compose up -d --build
```

Миграции БД выполняются автоматически при старте (контейнер backend ждёт PostgreSQL, применяет миграции Alembic, потом запускает FastAPI).

**Готово.** Откройте `http://<IP_СЕРВЕРА>:7777` в браузере. Войдите с логином и паролем из `.env`.

> ⚠️ Сами бэкапы в PostgreSQL **не хранятся**. Архивы лежат в Borg-репозиториях
> на томе бэкапов, поэтому даже полная потеря этой базы стоит реестра узлов,
> расписаний и истории — но ни одного архива.

## 3. Добавление узлов (Fleet Provisioning)

Перейдите во вкладку **Fleet**.

### 3.1 Добавление

Нажмите **Add Nodes**. Вводите IP-адреса в любом формате:
- По одному: `192.168.1.10`
- Списком: `192.168.1.10, 192.168.1.11, 192.168.1.12`
- Диапазоном: `192.168.1.50-60`
- CIDR: `10.0.0.0/24`

Укажите SSH-логин, пароль и порт. Форма предзаполняет значения по умолчанию (`user` / `admin` / порт `2222`) — измените при необходимости. Также вы можете предварительно задать несколько вариантов credentials в вкладке **Настройки**. В диалоговом окне добавления узлов эти предсохранённые варианты будут отображаться либо по вашему комментарию, либо по паре логина/пароля.

### 3.2 Что происходит при Bootstrap

Оркестратор подключается к каждому узлу параллельно (до 24 одновременно) и:

1. **Обходит мёртвые APT-прокси** — временно переименовывает недоступные конфиги, восстанавливает после.
2. **Устанавливает пакеты** — `python3`, `borgbackup`, `parted`, `e2fsprogs`, `dosfstools`.
3. **Прописывает SSH-ключ** — добавляет Ed25519 pubkey оркестратора в `/root/.ssh/authorized_keys`. Устанавливает `PermitRootLogin prohibit-password`.
4. **Создаёт пользователя `borg`** — системный пользователь с собственной парой SSH-ключей для отправки данных бэкапа.
5. **Собирает информацию об оборудовании и ПО** — тип диска, EFI UUID, hostname, версия ОС, разметка, сетевые интерфейсы, объем оперативной памяти, модель/ядра процессора, версия ПО Edge и версия рантайма Sentinel LDK.

С этого момента всё общение идёт по ключам — пароли не хранятся.

### 3.3 Auto-Prepare (разметка дисков)

Если у узла статус **NEEDS_FIX**, нажмите **Auto-Prepare**. Система:

1. Сохраняет `/etc/fstab` → `/etc/fstab.bak`.
2. Присваивает постоянные метки разделам: `edgeroot` (корень), `edgeboot` (boot), `edgelog` (логи), `edgestor` (данные), `EFI`.
3. Перезаписывает `/etc/fstab`, используя `LABEL=` вместо `/dev/sdX`. Система становится устойчивой к смене имён дисков (SATA ↔ NVMe).
4. Запускает `update-grub` + `update-initramfs -u`.

При ошибке на любом шаге оригинальный fstab восстанавливается автоматически.

## 4. Создание бэкапов

### 4.1 Ручной бэкап

1. Во вкладке **Fleet** нажмите кнопку **Backup** напротив нужного узла.
2. Нажмите **View Logs** для просмотра терминального вывода в реальном времени.
3. Оркестратор подключается к узлу по SSH, запускает `borg create`, данные стримятся в центральный Borg-репозиторий.
4. Результаты видны во вкладке **Архив** (размеры, временные метки, статистика дедупликации).

**Если репозиторий занят.** Borg допускает только одного писателя в репозиторий и держит блокировку всё время `borg create`, поэтому бэкапы в один шард идут по очереди. Прогон, пришедший, когда пишет другой, ждёт своей очереди — переспрашивает раз в десять минут в течение суток — а не падает. Неудачным он записывается, только если этот запас исчерпан. Если нужна настоящая параллельная запись, поднимите `BORG_SHARD_COUNT`.

**Как остановить.** Нажмите **Backup** на ноде, у которой бэкап уже идёт, — диалог предложит **Остановить**, а не запустит второй. Останавливается и прогон, ждущий очереди, и уже идущая передача; переданное сохраняется — следующий запуск продолжит с последнего checkpoint-а borg, а не начнёт заново.

Повторное нажатие **Backup** на той же ноде второй бэкап не запускает: дубль всё равно встал бы в очередь за первым.

### 4.2 Запланированные бэкапы (Группы)

Перейдите во вкладку **Расписание** → **Создать группу**.

Группа бэкапа определяет:
- **Какие узлы** входят в неё
- **Интервал** — 10мин, 30мин (оба варианта только для тестирования), еженедельно, ежемесячно, ежеквартально, ежегодно
- **Окно выполнения** — время начала / окончания
- **Лимит параллельности** — сколько узлов бэкапятся одновременно

#### Лимиты ресурсов (для группы)

| Настройка | Что делает |
|-----------|-----------|
| **Upload Rate Limit** (KiB/s) | Ограничивает пропускную способность сети для потока бэкапа |
| **CPU Quota** (%) | Ограничивает CPU на целевом узле (0–400% от ядра). Через `systemd-run --scope -p CPUQuota=...` |
| **Compression** | Выбор алгоритма: `lz4` (быстрый), `zstd:1`–`zstd:9` (лучшее сжатие). По умолчанию — `zstd:3`: лучший баланс степени сжатия и нагрузки на CPU для типичных данных бэкапа. Дедупликация ключуется по содержимому чанка до сжатия, поэтому разные настройки сжатия внутри одного репозитория совместимы — влияет только на новые чанки конкретного прогона. |
| **Checkpoint Interval** | По умолчанию рассчитывается автоматически и ограничен сверху, чтобы обрыв связи не стоил больше нескольких минут передачи. Можно задать вручную (секунды) |

#### Переопределения на уровне ноды

Отдельная нода может отличаться от своей группы. Откройте **Node Details** и задайте любое из этих значений; каждое падает на группу, затем на глобальную настройку:

| Переопределение | Значения |
|---|---|
| **Туннель через NAT** | Наследовать / За NAT / Напрямую |
| **Ограничение отдачи** (Мбит/с) | Пусто — наследуется лимит группы |
| **Оверрайд CPU-квоты** | Наследовать / Без лимита / свой процент от ядра |

#### Логика очереди

- **Динамическая параллельность**: если окно заканчивается, планировщик автоматически увеличивает параллелизм, чтобы успеть.
- **Ограничение по полосе**: при низком upload limit параллельность снижается для стабильности (рекомендуется выделять не менее ~2 MiB/s на поток, однако лимит может опускаться и ниже в зависимости от емкости сети).
- **FIFO-очередь**: узлы запускаются последовательно по временному сдвигу. Как только один заканчивает — следующий стартует.
- **Защита**: уже запущенные бэкапы могут завершиться после закрытия окна.

#### Политики хранения

Каждая группа может наследовать глобальную политику или переопределить собственную:
- **Интервальная** — хранить N ежедневных + N еженедельных + N ежемесячных
- **По количеству** — хранить последние N бэкапов
- **По временному окну** — хранить всё за последние N дней/недель/месяцев/лет

Глобальные умолчания (ротация, сжатие, CPU quota) настраиваются в **Настройках**.

Ротация запускается автоматически в 03:00 ежедневно через Celery Beat, затем `borg compact`.

### 4.3 Как дедупликация экономит место

Узлы распределены по `BORG_SHARD_COUNT` Borg-репозиториям (по умолчанию 1);
узлы одного репозитория записывают идентичные файлы на диск один раз.

| Сценарий | Занимаемое место |
|----------|-----------------|
| 1-й узел в шарде (базовая ОС 6 ГБ) | ~2.2–2.7 ГБ (сжатие 55–65%) |
| Каждый клонированный узел | +100–200 МБ (дедупликация 97%) |
| Узлы с небольшими различиями | +20–30% уникальных данных |
| Инкрементный запуск бэкапа | ~100–200 МБ |

Дедупликация не пересекает границу шарда, поэтому базовый образ хранится один
раз на шард. Это цена параллельности: Borg держит блокировку репозитория всё
время работы `borg create`, так что при единственном репозитории в каждый
момент писать может лишь один узел всего парка. Пять шардов дают пять
одновременных писателей ценой нескольких лишних гигабайт.

Шард узла — `node.id % BORG_SHARD_COUNT`, вычисляется один раз при постановке
на учёт и сохраняется в узле; заново он не считается никогда.

**`BORG_SHARD_COUNT` можно поднять позже. Понизить — нельзя.** Поскольку шард
хранится, добавление шардов оставляет каждый существующий узел в репозитории с
его архивами и направляет в новые только новые постановки на учёт. Поэтому
небольшое развёртывание может начать с `1` — это в точности та схема, что была
до шардинга, — и нарастить, когда вырастет:

```bash
# в .env
BORG_SHARD_COUNT=2

docker compose up -d --build
```

Это вся процедура. Форсированная команда SSH перечисляет репозитории,
доступные ключу, и выводится из этого числа, поэтому гранты парка нужно
переписать под новое значение — оркестратор делает это сам при старте.
Операция идемпотентна и отчитывается в лог бэкенда:

```
Shards: /data/borg/fleet, /data/borg/shard-1
2 borg grant(s): 1 to update, 1 already current.
```

`scripts/reauthorize_shard_access.py` никуда не делся и запускается вручную, а
с `--dry-run` показывает, что изменилось бы, ничего не меняя.

**Понижение не просто фиксируется, а не даётся.** Репозитории на диске задают
нижнюю границу настройки: каталог `shard-N` существует потому, что туда
направили узел, поэтому парк продолжает его обслуживать, что бы ни стояло в
переменной. При старте сообщается, что настройку переопределили и что выставить
вместо неё. Если бы понижение проходило, шард выпал бы из общего списка: ночной
prune перестал бы его посещать, а ключи его узлов — его разрешать, и бэкапы
падали бы с ошибкой про запрещённый путь, которая никак не указывает на
виновную настройку.

Единственное, чего нижняя граница не видит, — узел, назначенный на шард, куда
он ещё ни разу не писал: каталога нет, вывести неоткуда. Это проверяется
отдельно по базе, и при обнаружении такого узла **перезапись грантов
подавляется** — переписать их под меньшее число значило бы сузить доступ,
от которого эти узлы ещё зависят.

#### Сколько шардов нужно

**Не «по одному на каждые N узлов».** Группы бэкапов размазывают парк по
неделям и месяцам — для этого и существуют `interval`, `target_week` и
`randomize_days`, а Настройки → Нагрузка планировщика показывают получившийся
календарь, — поэтому число бэкапов, приходящихся на одну ночь, мало по замыслу
и ограничением обычно не является.

Число шардов задаёт **пиковая параллельность**: бэкапы, попадающие в один
репозиторий, идут строго по одному, потому что borg держит его блокировку всё
время работы `borg create`. Группа с `concurrency_limit: 5` на одном шарде
получает одного писателя, а не пятерых.

> **Правило: ставьте `BORG_SHARD_COUNT` равным наибольшему
> `concurrency_limit`, которую вы хотите реально получать.** По умолчанию 1 —
> схема до шардинга. Группам с лимитом 2 нужно два шарда, и не больше.

Календарь нагрузки это учитывает — доступная параллельность группы считается
как меньшее из её лимита и числа шардов, поэтому план, который переполнит
последовательное окно, показывается как не помещающийся, а не как нормальный.

Планировщик это тоже соблюдает, а не только календарь: он не запустит
одновременно больше бэкапов, чем есть шардов, — лишние всё равно не начнутся и
будут занимать воркер, вырабатывая `--lock-wait`.

**Что стоит решить до массовой постановки на учёт.** Шард узла назначается при
постановке и больше не меняется. Поднятие `BORG_SHARD_COUNT` позже направит в
новые репозитории *новые* узлы, а все уже поставленные останутся на месте: парк,
заведённый при значении 1, целиком останется на шарде 0, сколько потом ни
поднимай. Для парка, чьи группы размазывают нагрузку, это нормально — обычный
случай. Но если вы собираетесь завести сразу сотни узлов и хотите их
распределить, задайте число заранее.

Инкрементный прогон — малая доля от первого бэкапа: основная его стоимость это
обход файловой системы, а не передача данных. Поэтому один шард вмещает
несколько сотен последовательных бэкапов за типичное окно, и размазанное
расписание к такому и близко не подойдёт. Ваши собственные цифры показывает
Настройки → Нагрузка планировщика.

**Настройки → Хранилище → Ёмкость репозиториев отвечает на этот вопрос по
вашим данным.** Вместо того чтобы применять правило вручную, панель
проигрывает расписание вперёд и по каждому репозиторию показывает:

- самую загруженную ночь в процентах от окна выполнения этого репозитория;
- сколько узлов один репозиторий обслуживает за одну ночь и сколько выдерживает
  на том расписании, по которому парк действительно работает;
- сколько ещё узлов можно поставить на учёт, прежде чем самый загруженный
  насытится;
- каким станет показатель самого загруженного при большем числе шардов.

Длительность бэкапов берётся из записанного времени прогонов, поэтому прогноз
отражает те инкременты, которые парк действительно делает, а не условную
величину. Узел, который ещё ни разу не запускался, оценивается по *первым*
бэкапам парка — самым медленным, — так что в отношении первичной постановки на
учёт оценка не занижается.

Две вещи, в которых легко ошибиться и о которых панель говорит прямо:

- **Поднятие числа ничего не разгружает из того, что уже поставлено на учёт.**
  Строки прогноза расширения говорят об этом явно и показывают неизменившийся
  показатель самого загруженного. Когда самый загруженный репозиторий
  действительно заполнен, решение — переносить архивы, а не увеличивать число
  в `.env`.
- **Репозитории дают параллельные блокировки, но не параллельную полосу.** Там,
  где два бэкапа реально пересекались во времени, панель измеряет, что вытянуло
  хранилище, и если этого хватает на меньшее число писателей, чем есть
  репозиториев, называет ограничением хранилище. До тех пор она сообщает, что
  измерять нечего, вместо того чтобы напечатать число — на небольшом или только
  что развёрнутом парке это и есть ожидаемый ответ.

Единственное место, где дополнительные шарды реально окупаются, — **первичная
постановка парка на учёт**: первые бэкапы самые дорогие и приходятся все сразу,
поэтому на пяти шардах волна проходит примерно впятеро быстрее. Она бывает один
раз и может идти вне обычного окна, так что это повод начать с большего числа
шардов, а не держать их постоянно.

Если сомневаетесь — начните с меньшего. `BORG_SHARD_COUNT` можно поднять
позже, а каждый шард стоит одной лишней копии базового образа.

### 4.5 Как читать вкладку «Архив»

Четыре карточки в шапке отвечают на разные вопросы и намеренно не взаимозаменяемы:

| Карточка | Что означает |
|----------|--------------|
| **Занято на диске** | Измеренный размер Borg-репозитория и свободное место на его файловой системе. Настоящая цифра. |
| **Исходные данные** | Логический объём по всем успешным архивам, до сжатия и дедупликации. Накопительно за всё время. |
| **Экономия между нодами** | Сколько общий репозиторий экономит по сравнению с раздельным хранением базовых образов каждой ноды. |
| **Доля успешных** | Успешные архивы от общего числа. Ниже 80% становится красной. |

**Почему экономия считается только по базовым бэкапам.** Нода, которая бэкапится еженедельно и почти не меняется, каждый раз пишет гигабайты исходных данных ради пары сотен килобайт нового. Если учитывать такие прогоны, «нода редко меняется» засчитывается как дедупликация и завышает коэффициент в несколько раз. О хранилище говорят только базовые бэкапы: первая нода платит за весь свой образ, каждая следующая — лишь за то, чего у неё нет общего с остальными.

Базовый бэкап определяется по наибольшему дедуплицированному вкладу, а не по дате. Ретенция удаляет старые архивы, а суточная задача — соответствующие записи истории, поэтому самой ранней *уцелевшей* записью рано или поздно окажется инкремент, и коэффициент по нему улетел бы в тысячи.

Ниже — **Аналитика по флоту**, свёрнутая по умолчанию и подгружаемая только при раскрытии. Период 7, 30 или 90 дней либо любое значение от 1 до 365. Панели: надёжность, скорость передачи, длительность против окна группы, ёмкость. Метрика, которую система не может посчитать честно, показывается прочерком с указанием причины, а не нулём.

### 4.6 Удаление неудачных записей

Неудачные записи копятся от тестовых прогонов и известных сбоев и портят всю статистику надёжности на странице.

- **Одну запись** — кнопка **Удалить запись** в строке неудачного бэкапа.
- **Все неудачные у ноды** — **Очистить неудачные** в заголовке ноды; появляется, только если такие записи есть.

Успешные архивы здесь удалить нельзя: это восстановимые данные, и их судьба — за ретенцией или за кнопкой **Очистить архивы**. Недоступность репозитория удалению не мешает. Каждое удаление пишется в журнал аудита.

Checkpoint-архив, оставшийся от неудачного прогона, **сохраняется**, а не удаляется вместе с записью: в нём лежат уже переданные данные, благодаря которым следующая попытка продолжит с этого места, а не начнёт заново. Он убирается после того, как у этой ноды пройдёт успешный бэкап.

### 4.7 Как читать список флота

На кнопке **Backup** появляется отметка, если у ноды есть архив для восстановления, а дата в колонке **Last Backup** окрашена так же — строка читается одинаково в двух местах:

| Цвет | Значение |
|---|---|
| **Зелёный** | Бэкап есть, расписание соблюдается |
| **Жёлтый** | Плановый бэкап не выполнился |
| **Серый** | Расписание неприменимо — нода без группы или на паузе |
| **Без отметки** | Восстанавливать пока не из чего |

Нода, которая ни разу не бэкапилась **и** пропустила своё окно, показывает жёлтое **Never** — случай, который стоит разобрать первым.

Во время бэкапа на кнопке видна скорость, которую реально выдаёт borg, рядом с действующим для этого прогона лимитом (`42.3 / 50 Mbit/s`, или только измеренное значение, если лимита нет). По наведению на хостнейм показываются заметки ноды; хостнеймы с заметкой подчёркнуты.

**Веб-терминал.** Ctrl/⌘-клик по ячейке `IP:PORT` ноды открывает SSH-терминал прямо в браузере — локальный ssh-клиент или обработчик протокола не нужен. Полноэкранные программы (`htop`, `vim`, `top`) работают как обычно. По умолчанию каждый админ получает собственный интерактивный запрос пароля от ssh — оркестратор его не видит и не хранит — и подключается под тем логином, что сохранён в карточке ноды (при первом подключении он запрашивается и сохраняется, дальше переиспользуется без повторного запроса). Суперадмин всегда подключается ключом оркестратора, без запроса — и всегда под `root`, независимо от сохранённого логина ноды, поскольку bootstrap авторизует ключ оркестратора только для этой учётной записи. Переключатель **Настройки** → *Allow admins to use the orchestrator's key for the web terminal* распространяет такой же беспарольный доступ по ключу (и тот же вход под root) на остальных админов (по умолчанию выключен, менять может только суперадмин). Сессия без активности 15 минут закрывается автоматически; в журнал аудита пишется только факт открытия/закрытия сессии, никогда — её содержимое.

## 5. Восстановление на железо (Flasher)

Восстановление бэкапа прямо на физический диск, подключённый к оркестратору по USB.

### 5.1 Подключение диска

Используйте переходник **USB-to-SATA** или **USB-to-NVMe**.

| Тип диска | Правила подключения |
|-----------|-------------------|
| **SATA** | USB-SATA переходники обычно поддерживают горячее подключение. Просто вставьте USB в работающий сервер. |
| **NVMe** | Сначала вставьте M.2 в переходник, **потом** подключите USB к серверу. Никогда не вынимайте M.2 плату, пока переходник вставлен. Перед отключением — безопасное извлечение. |

### 5.2 Прошивка

1. Перейдите во вкладку **Flasher**.
2. **Справа** — выберите целевой диск. **Внимание**: Поскольку оркестратор поддерживает прошивку дисков напрямую с сервера, в списке будут отображаться все диски, кроме системного раздела самого сервера. Оператор должен выбирать целевой диск **ПРЕДЕЛЬНО ВНИМАТЕЛЬНО**! Диски, подключенные по USB, будут снабжены соответствующим ярлыком.
3. **Слева** — выберите узел-источник и снимок (архив) для восстановления.
4. Нажмите **Start Flashing**. Консоль логов покажет каждый шаг:
   - Полная очистка диска (`wipefs`) и разметка в GPT
   - EFI раздел отформатирован как `vfat` с историческим UUID
   - Системные разделы отформатированы как `ext4` (с отключённым `orphan_file` для совместимости с Debian 10)
   - `borg extract` распаковывает архив на смонтированный диск
   - Chroot: `mount --bind` для `/dev`, `/proc`, `/sys` → переустановка GRUB → `update-initramfs`
   - Сброс сети: удаление persistent-net rules, инъекция DHCP для `eth*`/`en*`
   - Переустановка Sentinel LDK (HASP): По дизайну HASP Sentinel защита от клонирования блокирует перенос лицензий при копировании на новое железо. В связи с этим в процессе записи диска служба Sentinel полностью переустанавливается и инициализируется заново.
   - Резервный EFI-загрузчик записывается в `EFI/BOOT/BOOTX64.EFI`
5. Дождитесь `Restore completed successfully!` — диск безопасно размонтирован.
6. Отключите переходник, установите диск в целевой узел, включите. Система загрузится со всеми данными на момент снятия бэкапа.

> 💡 **Миграция NVMe ↔ SATA**: fstab использует `LABEL=edgeroot` (а не `/dev/sdX`), поэтому бэкап с NVMe можно восстановить на SATA и наоборот. Интерфейс покажет предупреждение «drive type mismatch» — это штатно. Подтвердите и продолжайте.

## 6. Live-CD киоск (Рабочее место инженера и сетевое восстановление)

Основной сценарий использования системы — это центральный сервер бэкапов (в серверной или в облаке) и рабочие ПК/ноутбуки инженеров в офисе, которые загружаются с Live-CD киоска.

Работая в киоске, вы можете подключаться к серверу и прошивать целевые диски двумя способами:
1. **Сетевое восстановление (Network Restore)**: подключение по локальной сети или VPN и запись архивов напрямую из облака/сервера на целевые диски.
2. **Локальное автономное восстановление (Offline Local Restore)**: предварительная синхронизация нужных снимков бэкапа на свободное место загрузочной USB-флешки, что позволяет прошивать диски в полностью изолированной среде без подключения к интернету и сети.

Также поддерживается альтернативный сценарий запуска Live-USB непосредственно на самом восстанавливаемом edge-узле (без извлечения диска).

### 6.1 Подготовка и выписка ISO киоска

Процесс кэширования базового шаблона Debian и сборки кастомных ISO полностью автоматизирован. Вам не нужно собирать образы вручную через консоль:

1. Перейдите во вкладку **Live-CD и Киоски**.
2. В правой панели **Kiosk Control Panel** нажмите кнопку **Issue Live Kiosk**.
3. Заполните имя киоска (Friendly Name), контактные данные и комментарий.
4. Система автоматически создаст запись киоска и сгенерирует кастомный ISO-образ со встроенным уникальным токеном сопряжения.
5. Нажмите кнопку **Download** на строке созданного киоска, чтобы скачать готовый ISO-файл.
6. Если кэш был очищен или конфигурация требует обновления, нажмите кнопку **Re-create** для пересборки ISO.

#### Шаблонный ISO поддерживает себя в актуальном состоянии

Каждый ISO киоска собирается поверх общего шаблона — он показан в левой части
вкладки как **USB-Kiosk Client**. В шаблон входят сборка дашборда, скрипты
пейлоада и бинарник borg, поэтому обновление, затрагивающее что-либо из этого,
делает шаблон устаревшим, и карточка помечается **OUTDATED**.

Делать с этим ничего не нужно. Оркестратор каждые десять минут сверяет шаблон
с исходниками и пересобирает его при расхождении: карточка переходит в
**REBUILDING**, затем обратно в **READY**, обычно за пару минут. После этого
одобренные киоски помечаются на перепаковку поверх нового шаблона.

Два момента, о которых стоит знать:

- Упавшая сборка не повторяется на следующей проверке. Повторять одни и те же
  исходники каждые десять минут — это по полной сборке ISO на попытку без
  шансов на успех; блокировку снимает любое следующее изменение исходников.
  Сама ошибка попадает во вкладку «Логи» как задача `ISO_GEN`.
- Выпускать киоск во время пересборки шаблона можно — он будет собран, как
  только шаблон будет готов.

### 6.2 Запись ISO на флешку

Используйте один из инструментов (в режиме **DD**, не ISO):

| Инструмент | Платформа | Особенности |
|-----------|-----------|------------|
| [**Rufus**](https://rufus.ie/ru/) | Windows | При записи выберите режим **DD Image**. Режим ISO/GPT не загрузится. |
| [**balenaEtcher**](https://etcher.balena.io/) | Windows / macOS / Linux | Всегда пишет в DD-режиме. Просто выберите ISO и USB. |
| `dd` | Linux | `sudo dd if=technician_client_v1.iso of=/dev/sdX bs=4M status=progress && sync` |

> ⚠️ **Почему DD-режим?** ISO содержит гибридный загрузочный образ с кастомной разметкой. Запись в режиме ISO (например, в Rufus по умолчанию) сломает загрузочную структуру. Rufus спросит — всегда выбирайте DD.

**Требования к флешке**: минимум 32 ГБ (лучше больше), скорость записи ≥ 15-20 МБ/с. Рекомендуется флешка уровня Netac US5 и выше.

### 6.3 Синхронизация одного снимка

Вместо скачивания всей истории бэкапов узла (потенциально сотни ГБ) можно синхронизировать один конкретный снимок:

1. Во вкладке **Live-CD и Киоски** выберите целевой узел и нужный снимок.
2. Нажмите **Sync Snapshot**.
3. Бэкенд на лету создаёт временный мини-репозиторий через `borg export-tar` | `borg import-tar` и стримит его на USB.
4. Интерфейс показывает скорость, прогресс-бар и ETA в реальном времени.

### 6.4 Загрузка и восстановление

1. **Основной сценарий использования**: Вставьте подготовленную USB-флешку в ПК или ноутбук технического специалиста (например, в офисе) и загрузитесь с неё.
2. **Вторичный сценарий**: В качестве альтернативы можно вставить USB-флешку непосредственно в восстанавливаемый edge-узел и загрузиться с неё.
3. Если клиенту требуется VPN-соединение для связи с центральным сервером:
   - Поместите ваш конфигурационный файл WireGuard `.conf` прямо в корень раздела персистентности USB-накопителя (монтируется как `/media/usb-data/wg0.conf`), либо воспользуйтесь встроенной в веб-интерфейс киоска вкладкой **Network Settings** (сканирование QR-кода через камеру или ручной ввод).
   - Все сетевые подключения NetworkManager (`.nmconnection`) должны размещаться в папке `/system-connections/` на разделе персистентности (т.е. `/media/usb-data/system-connections/`).
   - Профиль VPN сохраняется на USB и автоматически подключается при следующей загрузке.
4. Киоск сам подключится к центральному оркестратору и покажет интерфейс Flasher.
5. **При основном сценарии (восстановление на ПК инженера)**: Подключите целевой диск к ПК/ноутбуку инженера через USB-переходник SATA/NVMe. Выберите подключенный диск в качестве целевого устройства (Target Device), выберите узел и архив бэкапа и запустите процесс записи.
6. **При вторичном сценарии (восстановление прямо на узле)**: Выберите в качестве целевого устройства встроенный внутренний накопитель узла, выберите снимок бэкапа и запустите запись.

### 6.5 Управление киосками

В панели **Live-CD & Kiosks** во вкладке **Kiosk Control Panel** вы можете:

- **Выпуск персональных ISO** — по кнопке **Issue Live Kiosk** с уникальным токеном сопряжения.
- **Подтверждение / Блокировка / Реактивация / Удаление** доступа подключенных киосков.
- **Редактирование метаданных киосков** — имя (Friendly Name), контакт и комментарий.
- **Перекомпиляция / Скачивание** ранее сгенерированных ISO из списка истории.
- **Лимит кэша образов (`max_kiosk_isos`)**: Настраивается в Настройках и задает максимальное количество кастомных ISO киосков, одновременно хранящихся на диске сервера (по умолчанию 5). При сборке нового образа, превышающего лимит, самый старый ISO-файл автоматически удаляется с диска для экономии места. Запись киоска при этом остается в БД, а статус в панели меняется на pruned (выгружен из кэша); вы можете в любой момент пересобрать его кнопкой **Re-create**.

## 7. Лицензирование Sentinel LDK (HASP-ключи)

Для edge-узлов с лицензированием Sentinel HASP.

### 7.1 Мониторинг статуса

При bootstrap оркестратор определяет версию Sentinel LDK. Если обнаружена, в деталях узла появляется сворачиваемая карточка **Sentinel LDK License Info**:
- **Active** (зелёный) — лицензия валидна
- **Expired** (оранжевый) — срок действия истёк
- **Clone Detected** (красный) — обнаружена смена оборудования
- **Disabled** (серый) — ключ или демон недоступен

### 7.2 Скачивание C2V-отпечатка

1. Откройте детали узла в **Fleet** → разверните карточку Sentinel.
2. Нажмите **Download C2V Fingerprint**.
3. Оркестратор запустит `hasp_update lf` + `hasp_update i` на узле по SSH. При отсутствии CLI — fallback на ACC API (`127.0.0.1:1947`).
4. Файл `.c2v` скачается в браузер.

### 7.3 Применение V2C-обновления

1. Откройте детали узла → карточка Sentinel.
2. Перетащите или выберите `.V2C` файл.
3. Оркестратор загрузит его на узел и выполнит `hasp_update u <файл>` по SSH.
4. Статус лицензии обновится автоматически.

## 9. Бэкап и восстановление базы данных

PostgreSQL оркестратора хранит все конфиги узлов, SSH-ключи, историю бэкапов, группы и настройки. Бэкапьте её.

### Автоматический дамп (cron)

Создайте `/opt/backup_db.sh`:
```bash
#!/bin/bash
BACKUP_DIR="/var/backups/edge_bro_db"
mkdir -p "$BACKUP_DIR"
FILENAME="${BACKUP_DIR}/db_backup_$(date +%Y%m%d_%H%M%S).sql.gz"

docker compose -f /opt/stacks/edge-bro/docker-compose.yml \
  exec -T db pg_dump -U postgres borg_orchestrator | gzip > "$FILENAME"

# Хранить 30 дней
find "$BACKUP_DIR" -type f -name "db_backup_*.sql.gz" -mtime +30 -delete
```

Добавьте в crontab (`crontab -e`):
```cron
15 3 * * * /bin/bash /opt/backup_db.sh > /dev/null 2>&1
```

### Восстановление

```bash
gunzip -c db_backup_YYYYMMDD_HHMMSS.sql.gz > recovery.sql

docker compose exec -T db psql -U postgres -d postgres \
  -c "DROP DATABASE borg_orchestrator;"
docker compose exec -T db psql -U postgres -d postgres \
  -c "CREATE DATABASE borg_orchestrator;"
docker compose exec -T db psql -U postgres -d borg_orchestrator < recovery.sql
```

После восстановления перезапустите контейнер backend, чтобы он подхватил данные.

## 10. Диагностика и сбор логов

При возникновении неполадок в работе оркестратора вы можете выгрузить логи напрямую через API либо собрать логи контейнеров на сервере.

### 10.1 Эндпоинты диагностики (API)
Эти эндпоинты защищены и требуют соответствующих сессионных кук/заголовков авторизации:

- **Системные логи демона**: `/api/tasks/debug-logs` (требуется роль Admin)
  - Возвращает последние 500 записей системных логов (ошибки и сообщения FastAPI, Celery воркеров и планировщика).
- **Логи административного аудита**: `/api/users/audit-logs` (требуется роль Superadmin или Admin)
  - Возвращает последние 1000 записей действий пользователей (входы в систему, изменения настроек, управление пользователями).
- **Логи консоли задач**: `/api/tasks/{task_id}` (требуется роль Kiosk или Admin)
  - Возвращает полный вывод консоли/Ansible-плейбука для конкретной фоновой задачи.

### 10.2 Логи контейнеров сервера
Для диагностики проблем на уровне Docker или получения вывода всех сервисов (Nginx, FastAPI, Borg SSH Server, Postgres, Redis, Celery) выполните на сервере оркестратора:

```bash
docker compose logs --tail=2000 > edge_bro_logs.txt
```
Приложите полученный файл `edge_bro_logs.txt` к обращению в техническую поддержку.

### 10.3 Ошибка `external volume "..." not found` при запуске

В старых редакциях `docker-compose.yml` все именованные тома были объявлены как `external: true` — это указывает Compose, что тома уже существуют и создавать их нельзя. При чистой установке их ещё никто не создал, поэтому `docker compose up` падает с ошибкой:

```
external volume "backup-edge-restore_apt-cache" not found
```

В текущих редакциях это исправлено — тома объявлены как `external: false`, и Compose создаёт их при первом запуске. Обновите код и запускайте обычным способом:

```bash
git pull
docker compose up -d --build
```

Если вы уже обошли проблему вручную, учтите: тома теперь называются `edge-bro_*`. Данные, записанные под старыми именами `backup-edge-restore_*`, автоматически не подхватятся — посмотрите список через `docker volume ls` и скопируйте то, что нужно сохранить:

```bash
docker run --rm -v backup-edge-restore_pg-data:/from -v edge-bro_pg-data:/to alpine cp -a /from/. /to/
```

### 10.4 Контейнеры здоровы, но ни один порт не отвечает

Симптом: `docker compose ps` показывает все сервисы поднятыми и здоровыми,
`docker exec` в любой контейнер работает, контейнеры видят друг друга — и при
этом панель на 7777, API на 8000 и borg-точка на 12345 не отвечают вовсе либо
принимают соединение и тут же его рвут. У узлов падают бэкапы; в логах самого
оркестратора ничего плохого нет, потому что с ним ничего плохого и не
происходит.

Причина — конфликт маршрутизации. Хост уже маршрутизирует диапазон, в который
Docker поместил сеть стека: VPN, туннель между площадками, другая
Docker-сеть, — а выигрывает более специфичный маршрут, поэтому трафик, который
хост отправляет контейнеру, уходит в туннель, а не на мост.

Сверьте, что маршрутизирует хост, с тем, что использует стек:

```bash
ip route
docker network inspect edge-bro_default -f '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
```

Если диапазоны пересекаются, выберите свободный и задайте его в `.env`:

```env
DOCKER_SUBNET=10.83.44.0/24
```

Сеть создаётся при старте, и переадресовать её на месте нельзя, поэтому для
применения изменения стек нужно остановить:

```bash
docker compose down
docker compose up -d
```

В текущих редакциях подсеть задана явно, а не отдана на откуп пулу Docker, так
что чистая установка попадает на `172.29.13.0/24`, если не переопределить.
Развёртывания, созданные раньше, могут до сих пор сидеть на том, что было
назначено автоматически; та же пара `down` / `up` переводит их на заданный
диапазон.

## 11. Мониторинг состояния флота (SMART и термоинтерфейс)

Пассивная оценка здоровья диска и отслеживание термоинтерфейса CPU,
отображаются как плашки на карточках DISK DRIVE и CPU каждой ноды.

### 11.1 Включение сбора данных на ноде

Сборщик ставится автоматически последним шагом каждого успешного
**Bootstrap** — и при первичной провизии, и при любой повторной. Для ноды,
которая проходит Bootstrap как обычно, вручную запускать ничего не нужно.
Ошибка установки пишется предупреждением в лог таска, но сам bootstrap не
проваливает — нода, которая уже корректно бэкапится, не должна помечаться
сломанной из-за телеметрии.

Установка выполняется плейбуком `backend/playbooks/deploy_monitoring.yml`,
который ставит POSIX-sh сборщик и systemd-таймер (`edge-bro-collect.timer`,
раз в 60 с), читающий температуры, счётчики энергии RAPL и I/O диска только
из sysfs — без раскрутки `smartctl`, с низким приоритетом I/O, без
прослушивания сети. Данные буферизуются в
`/var/log/edge/edge-bro/telemetry.jsonl` (лимит 16 МБ, раздел уже исключён
из бэкапов), пока оркестратор не заберёт их по существующему SSH-каналу. Лог
таска сообщает по каждой ноде, реально ли доступны RAPL, `drivetemp` и
`smartctl` — нода без RAPL всё равно получит SMART-оценку, но не
термопоказатель.

Чтобы поставить или переустановить сборщик на ноду **без** полного Bootstrap
— например, на ноду, спровизионированную до появления мониторинга — можно
запустить тот же плейбук напрямую:

```bash
docker compose exec worker ansible-playbook playbooks/deploy_monitoring.yml \
  -i "<node_ip>, ansible_user=root, ansible_ssh_private_key_file=/root/.ssh/id_ed25519"
```

### 11.2 Как читать плашки

- **Плашка SMART** — оценка 0–100, заливка от зелёного к красному. По клику —
  полные последние данные (подпоказатели по атрибутам, прогноз износа с
  выводом расчёта, задержка доступа) и график истории с выбираемыми
  метриками.
- **Плашка CPU** — статус термоинтерфейса: `OK` / `WATCH` / `ALERT` /
  `INSUFFICIENT_DATA`. Показывает оценённое тепловое сопротивление (θ, °C/Вт),
  а не процент — термоинтерфейс оценивается как «похож на соседей» или нет, а
  не по выдуманной шкале. `INSUFFICIENT_DATA` — честное состояние, когда
  истории нагрузки от бэкапов ещё не хватает для фита, подсказка объясняет
  причину (фита ещё не было / окна отброшены из-за недостаточной нагрузки).
- Нода оценивается двумя способами: относительно **сверстников с тем же CPU**
  (единичный выброс в своей когорте) и относительно **собственной истории**
  (дрейф от своего же бейзлайна). Каждый из них независимо может дать
  ALERT/WATCH.

### 11.3 Пороги

В `Settings` заданы глобальные значения по умолчанию для порогов температуры
SMART и интервала мониторинга; каждый переопределяется по ноде так же, как
лимит скорости бэкапа — для узлов, которые обоснованно греются сильнее
(например, на полном солнце). Мониторинг можно отключить по ноде, например
на время обслуживания.

### 11.4 Ноды, спровизионированные до появления мониторинга

Установка при Bootstrap срабатывает только на самом запуске Bootstrap. Нода,
которая была в статусе `READY` ещё до появления сборщика, сама его не
подхватит — перезапустите на ней Bootstrap либо примените плейбук напрямую,
как показано в §11.1.
