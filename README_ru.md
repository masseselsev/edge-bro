# Edge-B.R.O. — Backup & Restore Orchestrator

🇬🇧 [English](README.md) · [Usage Guide](README_USAGE.md) · 🇷🇺 [Русский](README_ru.md) · [Инструкция](README_USAGE_ru.md)

Централизованная система управления бэкапами и восстановления для парков edge-устройств на базе Debian. Полностью контейнеризована. Запускается одной командой `docker compose up`.

---

Девять постоянно работающих контейнеров в `docker-compose.yml` плюс две разовые задачи, которые запускаются только когда движку базы нужно обновление:

| Сервис | Назначение |
|--------|-----------|
| **frontend** | React SPA за Nginx. Панель управления с поддержкой тёмной и светлой тем. Вкладки: Fleet, Flasher, Архив, Расписание, Логи, Настройки. Три языка (EN/RU/UK). Встроенная терминальная консоль для логов. |
| **backend** | FastAPI на Uvicorn. REST API, парсер IP (CIDR / диапазоны / списки), трекинг задач. Определяет физические и VPN IP хоста через `/host/proc/1/net/` (пропускает docker-мосты). |
| **worker** | Celery worker в привилегированном режиме. Запускает Ansible-плейбуки и команды разметки дисков. Требует доступ к `/dev` для прошивки. |
| **worker-periodic** | Второй Celery worker на отдельной очереди. Берёт плановую и служебную работу, чтобы долгая прошивка или bootstrap не задержали тик планировщика. |
| **beat** | Планировщик Celery Beat. Запускает `borg prune` ежедневно в 03:00, применяет политики хранения. |
| **borg-server** | Изолированный SSH-сервер на порту 12345. Хранит Borg-репозитории — их `BORG_SHARD_COUNT` штук, поэтому писать одновременно может больше одного узла. Ключи узлов попадают в `authorized_keys` под форсированной командой `borg serve`, перечисляющей каждый шард через `--restrict-to-path`. |
| **db** | PostgreSQL 18. Инвентаризация, история, группы, настройки, учётные записи. |
| **redis** | Redis 7. Брокер задач + хранилище результатов Celery. |
| **apt-proxy** | Кэширующий APT-прокси на порту 3142. Bootstrap парка тянет одни и те же пакеты раз за разом; после первого узла они отдаются с диска. |

## Основные возможности

### Управление парком (Fleet)
- Регистрация узлов по IP-спискам, диапазонам (`192.168.1.50-60`) или CIDR-блокам (`10.0.0.0/24`).
- Параллельный bootstrap через Celery — до 24 узлов одновременно. Несколько вариантов credentials могут быть предзаданы в Настройках (в выпадающем списке отображаются либо по комментарию, либо по паре логина/пароля).
- Установка пакетов, инъекция SSH-ключей, сбор подробной информации об оборудовании и ПО (тип диска, EFI UUID, hostname, версия ОС, разметка, сетевые интерфейсы, объем оперативной памяти, модель/ядра процессора, версия Edge, версия Sentinel LDK) — всё через Ansible.
- **Встроенный веб-терминал**: Модальное окно с xterm.js терминалом через WebSocket (`Ctrl`/`Cmd` + клик по IP:PORT узла). Суперадминистратор подключается напрямую по ключу оркестратора; остальные администраторы получают стандартный интерактивный ввод пароля.
- **Защита от гонок при bootstrap**: Повторный провизионинг автоматически блокируется, если на узле в данный момент выполняется бэкап, исключая конфликт с установкой пакетов и перезапуском sshd.
- **Диалог выбора учётных данных**: Удобный запрос при провизионинге с предложением применить дефолтные credentials флота либо ввести индивидуальные для ноды.

### Подготовка дисков (Auto-Prepare)
- Присваивает постоянные метки файловым системам: `edgeroot`, `edgeboot`, `edgelog`, `edgestor`, `EFI`.
- Сохраняет уникальный UUID FAT32-раздела EFI для последующего восстановления.
- Перезаписывает `/etc/fstab` с монтированием по `LABEL=` — защита от смены `/dev/sda` ↔ `/dev/nvme0n1`.

### Бэкапы и дедупликация
- Push-модель: оркестратор подключается к узлу по SSH, запускает `borg create`, данные стримятся в центральный репозиторий.
- **SSH keepalive** настраивается через `.env` (`SSH_KEEPALIVE_INTERVAL`, `SSH_KEEPALIVE_COUNT`).
- **Лимиты ресурсов** для каждой группы бэкапов:
  - Ограничение скорости (KiB/s)
  - Ограничение CPU (0–400% от ядра, через `systemd-run --scope`)
  - Выбор алгоритма сжатия (`lz4`, `zstd:1`–`zstd:9`)
  - Интервал чекпоинтов — авторасчёт по скорости канала или ручная настройка
- **Шардирование репозиториев**: парк распределён по `BORG_SHARD_COUNT` независимым Borg-репозиториям (по умолчанию 1 — см. ниже). Borg удерживает блокировку репозитория на *всё* время `borg create`, а не на короткую критическую секцию, — поэтому при одном репозитории в каждый момент писать может ровно один узел парка, независимо от лимита параллельности группы. Каждый шард — ещё один по-настоящему параллельный писатель, а «Нагрузка планировщика» показывает доступную параллельность группы как меньшее из её лимита и числа шардов.
  - Считайте по **пиковой параллельности, а не по размеру парка**: группы и так размазывают парк по неделям и месяцам, поэтому ночной объём мал по замыслу. Ставьте `BORG_SHARD_COUNT` равным наибольшему `concurrency_limit` среди групп.
  - Шард узла — `node.id % BORG_SHARD_COUNT`, назначается при постановке на учёт и больше не меняется. Группы можно переназначать в любой момент, поэтому они не могут решать, где лежат *данные* узла; идентичность узла постоянна всю его жизнь.
  - Шард 0 — **это и есть** прежний `/data/borg/fleet`, не переименованный и не перенесённый, так что все существующие узлы продолжают бэкапиться и восстанавливаться ровно там же, где и раньше.
  - **`BORG_SHARD_COUNT` можно поднимать позже, но не понижать.** Шард узла хранится, а не вычисляется заново, поэтому добавление шардов оставляет каждый существующий узел в его репозитории и направляет в новые только новые постановки на учёт. Поднятие не требует отдельных шагов: SSH-гранты выводятся из этого числа, и оркестратор переписывает их сам при старте. Понижение *не даётся* — репозитории на диске задают нижнюю границу, парк продолжает их обслуживать что бы ни стояло в переменной, а при старте сообщается о переопределении.
  - **Ёмкость репозиториев** (Настройки → Хранилище) показывает, верно ли выбрано текущее число, вместо того чтобы выяснять это по переполненному окну. Для каждого репозитория выводится самая загруженная прогнозируемая ночь как доля его окна выполнения, сколько узлов один репозиторий выдерживает на том расписании, по которому парк реально работает, и что изменит поднятие числа — а для уже поставленных на учёт узлов не изменит ничего. Там, где бэкапы шли одновременно, дополнительно измеряется, что вытянуло само хранилище, и указывается, когда ограничивает именно оно, а не число репозиториев.
- **Сквозная дедупликация**: узлы одного шарда хранят идентичные файлы ОС единожды.
  - 1-й узел в шарде: экономия 55–65% (сжатие ~6 ГБ → ~2.5 ГБ)
  - Каждый клон добавляет лишь ~100–200 МБ
  - Инкрементные запуски: ~100–200 МБ уникальных данных
  - Дедупликация теперь идёт *внутри* шарда, то есть базовый образ хранится один раз на шард, а не один раз на весь парк. На однородном парке решает поштучный инкремент, и общий объём растёт всего на несколько процентов — параллельность стоит куда дороже этих лишних гигабайт.
- **Умный планировщик очереди**:
  - Динамическое масштабирование параллельности при нехватке времени окна
  - Автоограничение параллельности по полосе пропускания (может опускаться ниже 2 MiB/s на поток при необходимости)
  - FIFO-очередь с временными сдвигами; слоты освобождаются мгновенно
  - Защита выполняющихся бэкапов после закрытия окна
  - Время выполнения берётся из собственной истории узла, если она есть; для узла, который ещё не запускался, — из времени первых бэкапов по парку, и только затем из «байты ÷ лимит скорости». Узел с тридцатисекундным инкрементом и узел, заливающий первый полный образ, планируются по-разному.
- **Ротация**: по интервалам, по количеству или по временному окну. Глобально или с переопределением для группы. Запуск ежедневно в 03:00 через Celery Beat, затем автоматический `borg compact`.
- **Исключения**: настраиваются в UI. По умолчанию:

  | Шаблон | Назначение |
  |--------|-----------|
  | `/dev/*` | Системные устройства |
  | `/proc/*` | Виртуальная ФС процессов |
  | `/sys/*` | Информация sysfs |
  | `/run/*` | Временные файлы рантайма |
  | `/mnt/*` | Примонтированные ФС |
  | `/media/*` | Съёмные носители |
  | `/lost+found` | Восстановленные фрагменты |
  | `/var/log/edge/*` | Логи приложения Edge |
  | `/var/opt/edge/blobstore/*` | Локальное медиахранилище |
  | `/var/spool/edge/*` | Спул-директория Edge |
  | `/var/log/journal/*` | Логи systemd journal |
  | `/var/log/**/*.gz` | Сжатые ротированные логи |
  | `/var/log/**/*.1` | Ротированные лог-файлы |
  | `/var/hasplm/*` | Данные лицензирования Sentinel HASP |
  | `/etc/hasplm/*` | Конфигурация Sentinel HASP |


### Статистика архивов и аналитика по флоту
- Карточки в шапке: измеренный размер репозитория на диске, суммарный объём исходных данных, экономия между нодами и доля успешных бэкапов по всему парку.
- **Экономия между нодами** считается внутри каждого шарда и суммируется — узлы из разных репозиториев не могут дедуплицироваться друг с другом. Учитываются только *базовые* бэкапы. Если учитывать все архивы, повторный бэкап неизменившихся данных засчитывается как дедупликация — и цифра начинает измерять, насколько редко нода меняется, а не насколько плотно общий репозиторий упаковывает парк. Базовый бэкап определяется по наибольшему дедуплицированному вкладу, а не по дате, поэтому переживает удаление исходного архива ретенцией.
- **Аналитика по флоту** (свёрнута по умолчанию, загружается по требованию) за 7 / 30 / 90 дней или произвольный период:
  - *Надёжность* — доля успешных, просроченные ноды, серии подряд идущих отказов, частые причины. Просрочка считается от интервала группы самой ноды, поэтому месячная нода не подсвечивается через три недели после последнего запуска.
  - *Скорость передачи* — медиана и 10-й/90-й процентиль, самые медленные ноды, и упирается ли нода в собственный лимит.
  - *Длительность и окно* — время выполнения против окна группы, по худшему прогону, а не по медиане.
  - *Ёмкость* — суточный прирост, запас и наибольший вклад. Приводится как оценка сверху: удаление по ретенции не вычитается.
- **Очистка неудачных записей**: неудачные бэкапы удаляются по одному или разом по ноде — для тестовых прогонов и известных сбоев. Успешные архивы удалить нельзя: это восстановимые данные, и их судьба — за ретенцией или за очисткой архивов ноды. Оставшиеся от неудачного прогона checkpoint-архивы удаляются вместе с записью, каждое удаление пишется в журнал аудита.

### Мониторинг состояния флота (SMART и термоинтерфейс)
- **SMART-оценка**: `min()` по независимо оцениваемым подпоказателям (износ, резервная ёмкость, целостность, счётчики ошибок, температура, self-test), а не одно непрозрачное число — в интерфейсе всегда видно, какой подпоказатель определяет итоговую оценку. Жёсткие переопределения (провал health-check, pending/uncorrectable сектора, низкий резерв) ограничивают оценку сверху независимо от остальных подпоказателей.
- **Прогноз износа**: скользящий фит скорости записи против заявленного TBW диска, выдаётся как дата предполагаемой замены, а не голый процент, рядом всегда показан вывод (текущий износ, темп в сутки, число дней наблюдения) — а если фит ещё ненадёжен, вместо даты честно указывается причина.
- **Состояние термоинтерфейса**: тепловое сопротивление CPU→радиатор (θ) оценивается пассивно по нагрузке, которую уже создаёт каждый плановый бэкап, через IV-фит, корректирующий шум датчиков. Синтетическая нагрузка на флот не подаётся.
  - **Когортное сравнение** отмечает ноду, чья θ выделяется на фоне сверстников с тем же CPU.
  - **Дрейф относительно себя** отмечает ноду, чья собственная θ сместилась относительно её же истории, независимо от сверстников.
- **Плашки состояния** на карточках DISK DRIVE и CPU, заливка непрерывно от зелёного к красному. По клику — полные последние данные и график истории с выбираемыми метриками и глубиной, сохраняется по-пользовательски.
- **Пороги** (температура SMART, интервал мониторинга, вкл/выкл) глобальные с переопределением по ноде — та же цепочка наследования, что и у лимита скорости бэкапа.
- **Лёгкий сборщик**: POSIX-sh скрипт + systemd-таймер, читает sysfs раз в минуту с низким приоритетом I/O. Буферизует локально; оркестратор забирает буфер по уже существующему SSH-каналу — без открытых портов и новых учётных данных.

### Оповещения и инциденты (Alerts)
- **Центр управления алертами**: Настраиваемая вкладка «Настройки → Алерты», постоянное хранилище инцидентов в БД и колокольчик уведомлений в верхней панели для мгновенной реакции оператора.
- **Источники оповещений**:
  - **Мало свободного места (Low Storage)**: Предупреждает о приближении емкости дисков или хранилища бэкапов к критическому порогу.
  - **Узел недоступен (Node Offline)**: Отслеживает серию неудачных пингов и пропажу узлов из сети.
  - **Просроченный бэкап (Stale Backup)**: Выявляет ноды, пропустившие плановое окно резервного копирования согласно интервалу их группы.
  - **Здоровье SMART**: Срабатывает при появлении неисправимых секторов, критического износа SSD или сбоя самодиагностики.
  - **Аномалии охлаждения**: Сигнализирует о деградации термоинтерфейса или выходе температур за допустимые границы.
- **Тонкая настройка источников**: Каждый источник можно независимо включить/выключить, переопределив пороги и периодичность опроса.
- **История инцидентов**: Журнал событий с фильтрацией (все/открытые/подтверждённые/решённые) и кнопкой подтверждения оператором (acknowledge).
- **Отправка уведомлений**: Поддержка внешних каналов (включая Telegram-бота) с проверкой валидности паролей и токенов перед сохранением.

### Восстановление на железо (Flasher)
- Подключаете диск через USB-SATA/NVMe переходник → выбираете узел + снимок → прошиваете.
- **Предупреждение о локальной прошивке**: Поскольку оркестратор поддерживает прошивку дисков напрямую с сервера, в списке Flasher будут отображаться все диски, кроме системного раздела самого сервера. Оператор должен выбирать целевой диск **ПРЕДЕЛЬНО ВНИМАТЕЛЬНО**. Диски, подключенные по USB, будут снабжены соответствующим ярлыком.
- **Переустановка Sentinel LDK (HASP)**: По дизайну HASP Sentinel защита от клонирования не позволяет лицензии пережить прямое копирование разделов на новое железо. В связи с этим служба Sentinel полностью переустанавливается и инициализируется заново в процессе записи диска.
- Разметка GPT, восстановление EFI UUID, `borg extract`, chroot + GRUB, пересборка initramfs.
- Сброс сети: удаление persistent-net, инъекция DHCP для `eth*`/`en*`.
- Сервис проверки связи после восстановления обновляет статус узла до `RESTORED`.

### Live-CD клиент (киоск)
- **Автоматизированная компиляция**: Полностью автоматический конвейер подготовки базового кэша Debian и репаковки кастомных ISO киосков. Выписка и генерация персонализированных образов выполняется прямо из панели.
- **Основной сценарий использования**: Запуск на ПК/ноутбуке технического специалиста (например, в офисе). Клиент может прошивать целевые диски напрямую по сети (скачивая резервные копии с облака/сервера) или работать в полностью автономном режиме, предварительно синхронизировав нужные бэкапы на свободное место загрузочной флешки.
- **Вторичный сценарий**: Также поддерживается запуск Live-USB непосредственно на восстанавливаемом edge-узле в качестве альтернативы.
- **Синхронизация одного снимка**: генерирует временный mini-репозиторий через конвейер `borg export-tar` | `borg import-tar` — не нужно качать всю историю.
- Отображение скорости, прогресс-бар и ETA в реальном времени.
- **Управление киосками**: регистрация, подтверждение, блокировка, перепривязка из панели. Динамические ключи сопряжения. Возможность настройки лимита кэша (`max_kiosk_isos`) в Настройках: при превышении лимита старые образы автоматически удаляются с сервера, но их метаданные остаются в базе и могут быть пересозданы кнопкой Re-create.

### Интеграция с WireGuard VPN
- QR-сканер через веб-камеру (`jsQR`) для конфигов WireGuard, с ручной вставкой в качестве запасного варианта.
- VPN-профили сохраняются на USB в `/media/usb-data` с правами `0600 root:root`.
- Эндпоинты бэкенда: статистика туннеля (`wg show`), перезагрузка NM, up/down.

### Лицензирование Sentinel LDK
- Автоматическое определение `hasp_runtime_version` при bootstrap.
- Статусы лицензий в реальном времени: Active / Expired / Clone Detected / Disabled.
- Скачивание C2V-отпечатков через SSH (`hasp_update lf` + `hasp_update i`), с fallback на ACC API.
- Загрузка V2C-обновлений: drag-and-drop в дашборде, применение удалённо по SSH.

## Системные требования

### Сервер оркестратора
| Ресурс | Минимум | Рекомендуется |
|--------|---------|--------------|
| CPU | 2 ядра (x86_64) | 4 ядра |
| RAM | 4 ГБ | 8 ГБ |
| Сеть | 100 Мбит/с | 1 Гбит/с |
| Системный диск | 20 ГБ свободно | — |
| Кэш ISO | 20 ГБ свободно | Выделенный диск (`ISO_CACHE_HOST_PATH`) |
| Том для бэкапов | По размеру парка — см. ниже | Выделенный диск (`BORG_HOST_DATA_PATH`) |

**Расчёт тома для бэкапов** (квартальные бэкапы, хранение 5 последних = ~1.25 года). При достаточном количестве идентичного оборудования сквозная дедупликация Borg работает значительно эффективнее:

| Размер парка | Оценка (Разнородный парк) | Оценка (Идентичное оборудование) |
|-------------|---------------------------|----------------------------------|
| 50 устройств | ~60 ГБ | ~40 ГБ |
| 300 устройств | ~300 ГБ | ~150–200 ГБ |
| 1000 устройств | ~1 ТБ | ~500–600 ГБ |

Цифры — суммарные по всему парку, по всем шардам. Дедупликация работает внутри
шарда, поэтому базовый образ хранится один раз на шард, а не один раз на парк:
в колонке однородного оборудования это несколько лишних гигабайт против общего
объёма, где решает поштучный инкремент, — и взамен одновременно бэкапятся
`BORG_SHARD_COUNT` узлов вместо одного.

### Edge-узел (Целевое устройство)
- **Поддерживаемая ОС**: Debian 10 и выше, Ubuntu 18.04 и выше. Выпуски,
  репозитории которых уже переехали в архив дистрибутива, обрабатываются при
  бутстрапе; узел, настроенный на локальное зеркало, сохраняет его.
- **Поддерживаемое железо**: Материнские платы EMBC3000 и выше.
- **Спецификация**: 64-бит x86 CPU, 2 ГБ RAM (рекомендуется 4 ГБ), Ethernet или Wi-Fi.

### USB-накопитель для прошивки
- Минимум 32 ГБ (лучше больше), скорость записи ≥ 15-20 МБ/с. Рекомендуется флешка уровня Netac US5 и выше.

## Стабильность USB-оборудования

USB-переходники с UAS-драйверами (например, JMicron `152d:0581`) могут зависать при интенсивной записи `borg extract`. Принудительно переключите на стабильный legacy-драйвер `usb-storage`:

```bash
echo -e "options usb-storage quirks=152d:0581:u\noptions uas quirks=152d:0581:u" \
  | sudo tee /etc/modprobe.d/usb-quirks.conf
sudo usbreset 152d:0581   # или переподключите USB-кабель
```

Замените `152d:0581` на Vendor:Product ID вашего переходника из `lsusb`.

## Безопасность и авторизация

- **Авторизация**: логин + пароль, сессии через HTTP-only JWT-куки (`admin_session`).
- **Роли**:
  - **Superadmin** — управляет учётными записями (Настройки → Пользователи).
  - **Admin** — работает с системой, но не может управлять пользователями.
- **Авторизация киосков**: сопряжённые Live-CD используют заголовок `Authorization: Bearer <token>`. Offline-ISO поддерживают `?token=` в URL.
- **Первый запуск**: суперадмин создаётся из значений `.env` (`SUPERADMIN_USERNAME`, `ADMIN_PASSWORD`). Создаётся однократно — изменения `.env` не перезаписывают пароль, изменённый через UI. Для сброса: очистите таблицу `users` или обновите `.env` + перезапуск.

## Что оркестратор меняет на целевых узлах

Постоянного *сетевого* агента нет — каждое действие инициирует оркестратор
по SSH. Единственное локальное исключение — опциональный сборщик мониторинга
ниже: systemd-таймер, который только пишет в локальный файл и никогда не
слушает порт и никуда не стучится сам.

### Bootstrap (первичная подготовка)
| Действие | Детали |
|----------|--------|
| APT-пакеты | `python3`, `python3-pip`, `borgbackup`, `parted`, `e2fsprogs`, `dosfstools`, `util-linux` |
| SSH-ключ | Ed25519 pubkey оркестратора → `/root/.ssh/authorized_keys` |
| sshd_config | `PermitRootLogin prohibit-password` |
| Пользователь borg | Системный пользователь с SSH-ключами в `/home/borg/.ssh/` |
| Обход прокси | APT-прокси временно переименовываются в `*.disabled`, восстанавливаются после |

### Auto-Prepare (метки дисков)
| Действие | Детали |
|----------|--------|
| Метки разделов | `edgeroot`, `edgeboot`, `edgelog`, `edgestor`, `EFI` через `e2label`/`fatlabel` |
| `/etc/fstab` | Заменяется шаблоном по меткам. Резервная копия: `/etc/fstab.bak` |
| Загрузчик | `update-grub` + `update-initramfs -u` |

### Выполнение бэкапа
| Действие | Детали |
|----------|--------|
| Файлы на узле | **Не изменяются** — `borg create` работает в режиме только чтения |
| Процессы | Временные `borg create` + `ssh` туннель, завершаются по окончании |
| CPU/IO контроль | Опционально `systemd-run --scope -p CPUQuota=... -p IOSchedulingClass=idle` |

### Сборщик мониторинга (опционально)
| Действие | Детали |
|----------|--------|
| Скрипт | `/usr/local/sbin/edge-bro-collect.sh` — POSIX sh, чтение только из sysfs, без раскрутки smartctl |
| Расписание | systemd-таймер, раз в 60 с, `Nice=19` + `IOSchedulingClass=idle` |
| Буфер | `/var/log/edge/edge-bro/telemetry.jsonl`, ограничен 16 МБ, на разделе, уже исключённом из бэкапов |
| Сеть | На стороне ноды — никакой: ни открытых портов, ни исходящих вызовов. Оркестратор забирает буфер по уже существующему SSH-каналу `root@node`. |

Ставится автоматически после каждого успешного Bootstrap (и при первичной
провизии, и при повторной), через `backend/playbooks/deploy_monitoring.yml`.
Ошибка здесь пишется в лог, но никогда не валит сам bootstrap — нода, которая
уже корректно бэкапится, не должна помечаться сломанной из-за телеметрии.
